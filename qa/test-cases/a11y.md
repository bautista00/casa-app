about legibility, reach and keyboard operability — not screen-reader edge cases.

(`qa/reports/2026-09-14/L3-browser-pass1.txt`, `L3-browser-pass2.txt`,

### TC-A11Y-001 — Pinch-zoom works on every page

| | |
|---|---|
| **Priority** | P2 |
| **Type** | a11y |
| **Level** | L3 E2E |
| **Env** | E1 |

**Steps**
1. Load `/`, `/login`, `/callback`, `/casa/abc` at 390×844.
2. Read `document.querySelector('meta[name=viewport]').content`.

**Expected result**
No `maximum-scale` and no `user-scalable=no` — WCAG 2.1 SC 1.4.4 (Resize Text, AA).

**Last run** — RUN-2026-09-14 · **Verdict:** FAIL · **Bug:** CASA-018
**Notes** `"width=device-width, initial-scale=1, maximum-scale=1"` on all four routes, from
`src/app/layout.tsx:28`. Every Casa input already renders at 16 px, so the usual reason for the flag
(iOS auto-zoom on focus) does not apply.

### TC-A11Y-003 — Text and UI colours meet WCAG AA contrast

| | |
|---|---|
| **Priority** | P2 |
| **Type** | a11y |
| **Level** | L3 E2E |
| **Env** | E1 |

**Steps**
1. Probe each palette token's computed colour, convert to sRGB via a 1×1 canvas readback (the tokens
   are `oklch`, so string parsing gives wrong numbers — this is the step to get right).
2. Compute the ratio against `bg-card` and `bg-background`.

**Expected result**
≥ 4.5:1 for text at the sizes used (12–14 px), ≥ 3:1 for the rank pill and other UI components.

**Last run** — RUN-2026-09-14 · **Verdict:** FAIL · **Bug:** CASA-020
**Notes** Failing: white on `bg-crown` 1.77, `text-crown` 1.72, `text-effort-rapida` 2.26,
`text-accent` 2.55, `text-success` 2.87, `text-effort-pesada` 3.45. Passing: `text-destructive` 4.64,
`text-primary` 6.10, `text-muted-foreground` 6.93. A first measurement pass produced nonsense because
it parsed `lab()` strings as `rgb()`; the canvas readback is the method to repeat.

### TC-A11Y-004 — Keyboard focus is visible on every control

| | |
|---|---|
| **Priority** | P1 |
| **Type** | a11y |
| **Level** | L3 E2E |
| **Env** | E1 |

**Steps**
1. Tab through `/login` until the submit button is `document.activeElement`.
2. **Wait ~1 s** for `transition-all` to settle, then read `outline`, `box-shadow` and `border-color`.
3. Repeat for the email input.

**Expected result**
A clearly visible indicator — the shadcn button uses `focus-visible:ring-3 focus-visible:ring-ring/50`
rather than an outline, so the ring is a `box-shadow`, not `outline`.

**Last run** — RUN-2026-09-14 · **Verdict:** PASS · **Bug:** —
**Notes** Input: 3 px ring at 50 % of `--ring`, plus a primary border. Button after the transition
settles: the same 3 px ring and an opaque `--ring` border, `:focus-visible` matching.
**Caution for future runs:** measuring immediately after `Tab` catches the ring mid-transition at
~1.6 % opacity and 0.098 px, which reads as "no focus indicator". That nearly became a false positive
this cycle — always let the transition finish. Transcript in
`qa/reports/2026-09-14/L4-a11y-focus-transition.txt`.

### TC-A11Y-005 — Every input has a bound label

| | |
|---|---|
| **Priority** | P1 |
| **Type** | a11y |
| **Level** | L3 E2E |
| **Env** | E1 + E0 |

**Steps**
1. For every `input, select, textarea` on a page, assert a `label[for=<id>]`, an `aria-label` or an
   `aria-labelledby`.
2. Statically check the same for the signed-in forms.

**Expected result**
Every field is labelled.

**Last run** — RUN-2026-09-14 · **Verdict:** PASS · **Bug:** —
**Notes** `/login`: `[{id:"email", type:"email", labelled:true}]`. Static check of the signed-in forms:
`#name`, `#houseName`, `#code`, `#title`, `#notes`, `#dueDate`, `#dayOfMonth`, `#reward`, `#phone` all
have a matching `<Label htmlFor>`. The emoji, effort, assignee and weekday pickers are `<button>`
groups without a group role — they are operable and self-labelling, but a `role="radiogroup"` with
`aria-checked` would announce state properly. Recorded as an Observation.

### TC-A11Y-009 — Dialogs and sheets are keyboard-operable

| | |
|---|---|
| **Priority** | P2 |
| **Type** | a11y |
| **Level** | L3 E2E |
| **Env** | E2 |

**Steps**
1. Open the household switcher and the user menu in the header with the keyboard.
2. Check focus trapping, arrow-key navigation, Escape to close, and focus return to the trigger.

**Expected result**
Full keyboard operation, per the Base UI menu primitives.

**Last run** — RUN-2026-09-14 · **Verdict:** BLOCKED · **Bug:** —
**Notes** Blocker: the header only renders inside `AppShell`, which needs a signed-in session
(CASA-001). One thing to check first on the next run: both `DropdownMenuTrigger`s wrap a `<Button>`

primitive renders as a slot. That would be invalid HTML and would break keyboard activation — the
signed-out pages reported `nestedButtons: 0`, but they do not contain this component, so the question
is still open.
